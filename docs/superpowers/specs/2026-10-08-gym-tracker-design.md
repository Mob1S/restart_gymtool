- **日期**：2026-10-08
- **状态**：现行有效。综合 2026-09-15 起全部设计与实施记录

## 1. 一句话与三条红线

先说不可让步的三条，其余所有设计都是在这三条之下做的取舍。

| # | 红线 | 落地形式 | 谁在守它 |
|---|---|---|---|
| 1 | **训练记录永不丢失** | 每完成一组**立刻**写 SQLite，不等训练结束；休息计时用时间戳而非累加器 | `setRepo.completeSet`、`set_entry.rest_started_at` |
| 2 | **绝不伪造数据** | 没有的分就留空，不补均值；算不出的点就不画，不补 0、不补估算 | `importRepo`、`domain/progress.ts` |
| 3 | **不把估算说成实测** | e1RM 处处标注「估算 · 仅供参考」；容量标注口径；提示标注「粗略参考」 | `domain/metrics.ts`、界面文案 |

第 1 条是产品底线（丢一次用户就再也不会信任它），第 2、3 条是**信任底线** —— 一份被美化的曲线，比一份空白的曲线更糟。

### 2.2 每一次转折都是被现实推着走的

这段历程里最有价值的部分不是「做了什么」，而是**哪条设计被现实推翻了**。逐条记录：

| 时间 | 当初的设计 | 现实 | 修正后的设计 |
|---|---|---|---|
| 09-16 | 记录页：大数字拖动调值 | 手上有汗、屏幕可能湿，纯拖动会「想调 2.5kg 却滑过头」 | 保留一对缩小的 +/− 做精确微调。**10-04 复核再次确认二者互补而非重复**（拖动管大跨度 20→60，步进器管微调），只是把步进器降为次级视觉 |
| 09-16 | M2 第一版记录页**一次训练只能练一个动作** | 用户真机用一次就发现：**换不了动作** —— 这是一处**功能性缺口**，「App 无法完成任何一次真实训练」 | 顶部横向动作条 + `＋` 打开动作选择弹层（按肌群分组、拼音序、带搜索）。界面缺陷只有真机用一次才暴露，§7.1 |
| 09-16 | 新训练的动作清单**写死从深蹲开始**（`startNew` 里 `all.find(e => e.name === '深蹲')`，那是为「别让用户第一屏面对空列表」偷的懒） | 用户手机上「每次训练都以深蹲开始」 | 改为复制上一次**已结束**训练的动作组合与顺序；没有历史时开一场空训练。**连带发现空训练是条死路**（只有一句「这次训练还没有动作」，没有任何添加入口）→ 补整宽「＋ 添加动作」。顺带修掉一个隐患：复制动作时若不预建第一组，`completeCurrentSet` 直接 return，用户点「完成这组」会**静默无反应**（抽 `addExerciseWithFirstSet`） |
| 09-21 | 好意在 v1 就有的「沿用上次动作」 | 用户原话：*「第三次了我还接着第二次训练去练。」* 而且永远从深蹲开始 | 查出五处漏洞，把训练生命周期做成状态机（§3.4） |
| 09-21 | §2.4：**不加时间上限**，理由是「正常流程下不会留下未结束的训练」 | 旧包持续产生未结束训练，用户库里实测有 2 场 9/16 的残留；修复只是让它们**看得见**了 | **此条至今存疑，未解决**（§10.1）。这是「不加兜底」这个决定需要重新考虑的现实证据 |
| 10-04 | §9：**不做深色模式手动开关**（手动开关属于新功能） | 用户直接推翻 | 做了，且必须是**三态** `system/light/dark`，不是布尔（§4.4）。原文**故意保留**在旧文档里不删，好让「当时的范围」和「后来为什么变了」都能被读到 |
| 10-04 | 演示数据打算给 `demoExecutor` 补 SQL 分发 | 那个执行器按 SQL 形态匹配，每加一条语句就要补一条分支 | 10-07 改为**在 web 上把不可用入口隐藏**，一条分发分支都没补（§9） |
| 10-07 | 「新训练复制上一场」 | 用户原话：*「这和每个健身分化循环里的逻辑不符合」* —— 等于假设每个人每次都练同一套动作 | 换成用户自定义的**分化循环计划**，轮转优先、无计划时回落到旧逻辑（§3.5） |
| 10-07 | 删动作的「先留着」= `deleteCompletedSetsOf`（删光所有组，靠「sets 为空」把界面摘掉） | 那会把用户**练过的组也删掉**，而用户选它的意思恰恰是「别删我的记录」 | 改成 `deleteIncompleteSetsOf`：删占位组、**留已完成的组**；判据随之从「sets 为空」改成「还有没有未完成的组」 |
| 10-07 | 计划排序用「两句 `UPDATE ... WHERE position = ?` 对调」 | 实测在 `node:sqlite` 上**静默无效** —— `position` 没有唯一约束，第一句执行后两行同处一个 position，第二句同时命中、一起改回原处，「顺序纹丝不动且不报错」；先 SELECT 出 id 再按 id 定位**同样无效** | 只有「挪到临时位置 −1 → 目标行补位 → 被移动行落位」三步真能互换。**这类 SQL 不要靠推理，在真实引擎上跑一遍**（特征是不报错），两条测试红了才发现 |

## 3. 设计思路：这个项目的七个核心取舍

这一节是全文的重心。每条都是「当时为什么这么定」+「否掉了什么」，因为**只写结论的设计文档，看不出判断力在哪**。

### 3.1 技术栈：Expo / React Native，而不是 PWA 或原生 Android

| 方案 | 否决理由 |
|---|---|
| **PWA**（网页 + 添加到主屏幕） | 锁屏后计时与通知不可靠；将来用 Capacitor 转 APK 时，浏览器沙箱里 IndexedDB 的数据**无法自动迁移**到原生壳；界面仍在 WebView 中渲染 |
| **原生 Android**（Kotlin + Compose） | 环境需约 10GB 工具链；iOS 与小程序将来全部重写；编译-安装-查看的反馈循环更慢 |
| **Taro / uni-app** | 唯一能同时产出小程序的方案，但 RN 支持不成熟、手感打折，而小程序只是「将来可能」 |

选 Expo 的**已知代价也如实记账**：界面渲染在手机上，开发过程中看不到画面，UI 迭代依赖用户真机反馈。这条代价最终在 10-04 被网页预览打掉（§4.5），前后用了 19 天。

### 3.2 数据存储：纯本地，但把两个接缝先留出来

不做云同步（会让工作量翻倍，且产品价值尚未验证），但架构上先留好两处缝：

1. **Repository 接口层** —— 界面只调 `getLastPerformance(exerciseId)` 这类函数。将来加同步，改的是这一层，界面一行不动。
2. **导出 / 导入 JSON 是一等功能** —— 既是防丢数据的备份，也是将来换设备、换实现的迁移通道。

配套一条**硬性约束**，它是全部「将来好改」的基础：

> **`app/` 和 `components/` 永远不直接 import `db/`，只能 import `repositories/`。**

### 3.3 记录界面：聚焦当前组，不是全览列表

屏幕上只呈现**当前这一组**，拇指永远停在同一个位置，不需要瞄准。

| 布局 | 结论 |
|---|---|
| **B. 聚焦当前组** | ✅ **选定** |
| A. 全览列表（所有组摊开，点行内 ✓） | 点击目标小；单手够不到顶部；改数值需跳转 |
| C. 列表 + 底部常驻操作条 | 屏幕空间紧张，相比 B 的收益不足以抵消复杂度 |

配套细节：新的一组**预填上次该组的数值**；动作名下方常驻「上次这个动作的成绩」（渐进超负荷最需要的信息）；「第 N / M 组」的 M 默认沿用上次组数；完成时一次轻微震动，**让用户不用盯着屏幕确认**；记录全程屏幕常亮。

### 3.4 组间休息：正计时，不是倒计时

**这是本 App 与常见健身 App 最重要的区别**，也是用户的明确要求。

> 用户休息多久就记多久，数据是**观察**出来的，不是**规定**出来的。倒计时会催人，而每一次休息都因此成为一条可分析的数据。

实现上有一条不可妥协的约束：**计时基于 `rest_started_at` 时间戳，用 `now − start` 算，不用 `setInterval` 累加**。哪怕 App 被系统挂起十分钟，算出来的休息时长依然准确。`rest_seconds` 存在「本组做完之后」那一段休息上（第 3 组做完、第 4 组开始前的休息写在**第 3 组**），于是「开始下一组」只需写一条记录。

### 3.5 训练计划：只存动作清单与顺序，轮转指针不单独存

两条决定，各自都在消灭一处「第二真相」：

**① 计划里不存目标组数 / 目标重量 / 目标次数。**
目标是计划的一部分时，用户每改一次计划都要维护几十个数字；而「上次练了多少」本机已经自动沿用了（`setRepo.getLastPerformance`），计划再写一份就是第二处真相，两处必然打架。

**② 轮转指针不单独存，从 `session.template_id` 推导。**

```
今天该练哪一套 =
  取「最近一场已结束、且 template_id 非空」的训练所用模板
  → 在计划列表里找到它的位置 → 下一套（循环回到第一套）
  没有计划             → 沿用旧逻辑（复制最近一场已结束训练的动作）
  有计划但一场都没练过   → 第一套
  上一场用的模板已被删除 → 第一套
```

多存一个「下一个该练第几套」的字段，就要在**跳过、删除计划、导入记录、导入备份**四条路径上同步维护它；而它一旦与事实不符，表现是「莫名跳了一套」—— 用户看得见，但很难解释。

### 3.6 指标口径：区分「口径」与「估算」

**容量负荷（volume load）—— 这是口径问题，不是精度问题。**

```
总容量 = Σ (weight × reps)，只累加 is_completed = 1 的组，单位 kg
```

文献里 "volume" 的用法并不统一（总次数 / 组数×次数 / 含重量的 volume load）。本 App 采用最后一种，因此：文档与代码一律用准确说法「容量负荷 / volume load」；界面标注为「**总容量（重量 × 次数）**」；**不与采用其他口径的 App 或研究数据做横向比较**。

**估算 1RM（e1RM）—— 这是估算问题，必须标注误差与范围。**

```
e1RM = (Epley + Brzycki + Lombardi) ÷ 3
Epley    w × (1 + r/30)
Brzycki  w × (36 / (37 − r))
Lombardi w × r ^ 0.10
```

取平均是为了**降低单一公式的偏差，不代表更准**。适用范围：只在 `2 ≤ r ≤ 10` 计算；`r = 1` 直接返回 `w`；`r > 10` 返回 null 且**界面必须不显示**（外推严重失真）。

> **公式一旦确定，不得中途更改** —— 换了公式，「进步」页的历史曲线会出现无解释的断层。代码上的落实方式：公式只有 `domain/metrics.ts` 一份实现，`domain/progress.ts` 一律调用它，不重写。

### 3.7 训练后反馈：给一句诚实、粗略的话，并**必须包含正反馈**

| 条件 | 类型 | 文案示例 |
|---|---|---|
| `drop ≤ 0` 且（`avg_rest ≤ 180s` 或 `null`） | ✅ **正反馈** | 「5 / 5 / 5 / 5 全程稳住了，节奏合适」 |
| `drop ≤ 0` 且 `avg_rest > 180s` | 💡 **加重提示** | 「全程 5 次稳定，平均歇了 3 分 20 秒 —— 还有余力，可以考虑加重量」 |
| `drop = 1` | ⚠️ 轻微提醒 | 「末组 5 → 4，下次这个动作可以多歇 15 秒」 |
| `drop = 2` | ⚠️ 提醒延长 | 「末组 5 → 3，下次可以多歇 30 秒」 |
| `drop ≥ 3` | ⚠️ 延长 + 归因提示 | 「末组 5 → 2，多歇 30 秒试试；如果还是掉，可能是重量偏大」 |

四条**强制性要求**：

1. **必须把次数数组原样显示**（「5 / 5 / 5 / 3 / 3」）—— 只给结论不给原始数字，用户无法核对，也不会相信。
2. **必须标注「粗略参考」** —— 不得表述为科学建议或个性化处方。
3. 建议增量固定两档（15 / 30 秒），**不做百分比、不输出「最佳休息时长」**。
4. 已完成组数 < 3 时**明确沉默**，不给任何提示。

**明确不做**：不建统计模型、不做跨训练推断、不声称能算出「你的最佳休息时长」。理由是该领域 2024 年的系统综述与 meta 分析明确指出组间休息最优值**至今没有共识**，且**同一个人在不同训练日的反应存在明显差异**。任何声称能算出精确数值的算法都是过度承诺。

**为什么正反馈是硬性要求**：只挑毛病、从不肯定，用两周就会被无视。

**一条被替换的规则**：原设计有「缩短休息」提示，现替换为 `drop ≤ 0` 且休息偏长时的**加重提示**。理由 —— 全程稳定却歇很久，真正的信号是「还有余力」，该加重量；缩短休息只是副作用，不是目标。

## 4. 跨领域不变量与硬性规则

以下规则跨多个模块，违反任何一条都会以「很难排查」的形式表现出来。

### 4.1 数据与状态不变量

| # | 不变量 | 由谁把守 |
|---|---|---|
| 1 | `SELECT COUNT(*) FROM session WHERE finished_at IS NULL` **永远 ≤ 1**，且这条记录**只可能由进程被非正常终止产生** | `startNew` 的 `'conflict'` 分支（§5.2） |
| 2 | **同一时刻只可能有一场进行中的训练** | 同上；10-07 的改造**不得削弱**它（新的 `startNew` 仍先 `resume` 探一次） |
| 3 | **每完成一组立刻落盘** —— 这是可靠性要求，不是优化 | `completeCurrentSet` → `setRepo.completeSet` |
| 4 | **计划里的动作必须存在于动作库** | `template_exercise.exercise_id` 引用 `exercise(id)`；动作库只归档不删除 |
| 5 | **导入的记录不特殊** —— 导进来的、手填的、本机练的在库里完全同构 | 历史列表、进步曲线、「上次练了多少」三处**不需要为导入写任何特判** |
| 6 | **删除必须不可逆** | 记录页的写保护 + 总结页的兜底加锁（§5.2） |

### 4.2 语义化的判据纪律

> **判据两边必须用同一条。**

「还有没有**未完成**的组」同时是「记录页能不能再记一组」的条件和「动作该不该从记录页摘掉」的判据。10-07 那条 bug 就是判据写岔了：界面判「一行 set 都没有」（`keep` 保留已完成组后恒不成立），测试里也写错同一个判据 —— **两边同时错的时候，只有端到端测试能发现**（§7.3）。

### 4.3 排序：`rowid` 兜底不能省

时间戳只有毫秒精度，同毫秒的两场训练会完全并列，此时 SQLite 按扫描顺序返回（先插入的在前），**语义就反了**。因此所有按 `started_at` / `finished_at` 排序的查询一律补 `rowid` 兜底。对应的测试**故意不 sleep**，并先断言 `second.startedAt === first.startedAt` 确认撞车真的发生。

> **不要用 `sleep(5ms)` 绕开这个问题** —— 那只是把不确定性藏起来。

### 4.4 迁移：绝不修改已发布的项

| 版本 | 内容 | 触发场景 |
|---|---|---|
| v1 | 四张表 + `app_meta` | 全新库 |
| v2 | `app_setting`（用户偏好键值表） | 主题模式 |
| v3 | `split_template` / `template_exercise` + `session.template_id` | 分化计划 |

**不能并进旧项**：v1/v2 早就发布过，库里的 `schema_version` 已是 2 的库不会再跑它们（`migrate()` 只跑 `version > current` 的项），新列会永远加不上。因此每轮都**追加**一项，并配一条回归测试：手工造一个「只跑到 vN-1」的库，验证它升到 vN 后有表/列可用。

**另外两条具体约定**：

- `app_meta`（库结构，进备份、进迁移）与 `app_setting`（用户偏好，跟着用户走）**分开是有意的**，语义不同。
- `session.template_id` **刻意不写外键**：`ALTER TABLE ... ADD COLUMN` 加上的列级外键在 SQLite 里不会被后续写入强制（实测），写一个不生效的约束只会误导后来的人；改为明文约定 —— 删计划时由 `templateRepo.deleteTemplate` 把引用它的 `session.template_id` 置空。

### 4.5 网页预览的定位（不是验收）

| 事实 | 后果 |
|---|---|
| 网页版的数据库与手机**完全隔离**（`expo-sqlite` 在 web 上走 WASM，落到浏览器存储） | 碰不到真机上的真实记录；演示数据**只写网页版**，不进任何 seed 文件 |
| `react-native-web` 与真机在**字体度量、阴影、触感**上有差异 | 最终手感仍需在手机上确认 |
| `demoExecutor` 是**按 SQL 形态分发的内存假库，不是 SQL 引擎** | 计划管理、删记录、导入在预览里**本来就是「点了没反应」** |
| 因此 | 10-07 的选择是**在 web 上隐藏这三个入口**（一个常量 `isWebPreview`，四个界面 import），而不是给假库补一套 SQL 分支 |

> **一项具体修正是被测试逼出来的**：这个常量不能用 `Platform.OS === 'web'` 写。那需要 `import { Platform } from 'react-native'`，而 react-native 的入口是 ESM，jest 的 `testEnvironment` 是 `node`，加载不了它 —— 于是**任何间接 import 这个常量的模块都会在测试里炸**。改成**平台解析**：`src/lib/preview.ts` 为 `false`（无任何 import，node 下安全），`src/lib/preview.web.ts` 为 `true`，Metro 打包时优先取 `.web.ts`。这与 `database.tsx` / `database.web.tsx` 是同一套机制。

## 5. 现状设计规范

### 5.1 分层

```
app/          13 个路由文件  expo-router（文件即路由）—— 只调 repositories，永不 import db/
src/
  ui/         11 个文件      纯视觉层：主题、tokens、9 个基础组件。不碰数据库、不含状态、只回答「长什么样」
  components/  6 个文件      可复用业务组件（Stepper / DragNumber / RestTimer / TrendChart / …）
  store/       3 个文件      Zustand：当前训练状态 + 休息计时 + 主题偏好
  repositories/11 个文件     ← 接缝：SQL 只出现在这一层
  domain/      9 个文件      纯逻辑，无 IO，全部可单测
  lib/         9 个文件      无状态工具（格式化、图表几何、文件读写…）
  db/          6 个文件      schema / 版本化迁移 / SqlExecutor 抽象
```

**三条分层规则**（硬性）：

1. `app/` 与 `components/` 永远不直接 import `db/`，只能 import `repositories/`。
2. SQL 只出现在 `src/repositories/`。
3. 纯逻辑只出现在 `src/domain/`（**可单测是它必须留在这里的理由**）—— 决策逻辑写进 store 就没法单测「只有一套计划时永远轮到它」这类边界。

**`SqlExecutor` 只有三个方法**（`run` / `all` / `first`），生产用 `expo-sqlite` 实现，测试用 `node:sqlite` 实现，同一套仓储代码两边都跑。任何仓储函数只收这个接口，永远不收具体数据库对象。

### 5.2 训练生命周期状态机

| 触发 | 动作 | 结果 |
|---|---|---|
| 被误杀 / 强杀 | **什么都不做** | 库里留下唯一一条 current；下次启动 `resume` 捡回来 |
| 点「结束训练」 | 写 `finished_at` **并立即清空内存** | 进历史；主页从此不再出现「继续」 |
| 存在 current 时点「开始新训练」 | **不新建**，返回 `'conflict'` → 界面问一句 | 「接着练」= 进那场；「结束它，开始新的」= 先 `endWorkout` 再建新的 |

**第三行是这次修复的核心：「开始新训练」永远不能产生第二条未结束记录。**

三个配套细节，每个都对应一个真实 bug：

- **冲突时必须把那一场装进 store**（而不是只返回一个 id）：界面选「接着练」后直接导航到 `/session/[id]`，store 里没有 `exercises` 的话那一屏会误判成「这次训练还没有动作」，给用户一个空的记录界面。顺带修掉一个竞态：主页刚挂载、`resume` 还没跑完时点击「开始新训练」。
- **`endWorkout` 立刻清内存**是安全的，因为总结页按路由参数 `id` **从库里读**，不依赖 store。这样「结束了但没保存」这个中间态**就此消失** —— 它正是漏洞 1 的来源。
- **`resume` 恢复练到哪个动作**：取这场训练里 `completed_at` 最大的那一组，它归属的 `session_exercise` 在列表里的下标就是当时在练的动作（一组都没完成 → 0）。**纯查询，不加字段、不做迁移。** 正在休息的情况自动落在同一个答案上：`startRest` 就是对完成的那一组调用的，不需要第二条判定。已知不精确的只有一种：切到第 4 个动作但一组都没做就被杀 —— 会回到第 3 个动作，**明确接受**。

**防御性闸门**：`addExercise` / `completeCurrentSet` / `beginNextSet` 入口加一句「`session.finishedAt !== null` 就直接返回」。正常情况下 `endWorkout` 已清空 store，这一层是防**将来有人把已结束的训练塞回 store** —— 那个 bug 就是这么来的。

**一处有意的界面偏离（三按钮 → 两按钮）**：设计里写的是 `[接着练] [结束它，开始新的] [取消]`，实现是**两个按钮 + `cancelable: true`**。原因：Android `Alert` 最多三个按钮，且 RN 的映射顺序是 `[neutral, negative, positive]`（`buttonPositive = validButtons.pop()`）—— 三个按钮时必有一个落进**加粗主按钮位**，「无论放哪个都是误导」。

**两处被真机逼出来的设计细节**（都在这轮之前就存在，只是没人发现）：

- **30 分钟休息闸门**：完成一组后不按「开始下一组」，`rest_started_at` 会一直留着 —— 重开 App 被堵在休息页，而「这段荒唐时长会污染休息数据」。补 `domain/rest.ts` 的 30 分钟判定 + `setRepo.cancelRest` + `store.loadExercises`。
- **这一段暴露了测试的空白区**：当时 79 个断言**全在 `domain/` 与 `repositories/`，中间的 store 层（编排层）完全没有测试**。补 store 测试正是从这次事故开始的。

**状态转移里被否决的两种兜底**：不加「最后一次记录超过 N 小时就作废」，也不做「每次冷启动都问一句」。时间上限和每次询问都是在**替一个不该出现的状态做兜底**，而把「结束」变成不可逆的更准确、也不需要用户多点一下。（**这条仅对正常流程成立 —— 存量数据是例外，见 §10.1。**）

### 5.3 数据模型（schema v3）

```
exercise ──────────< session_exercise >──────── session
                            │
                            └──< set_entry

split_template ────< template_exercise >────── exercise
                            ▲
        session.template_id ┘（不加外键，由 deleteTemplate 置空）
```

| 表 | 说明 |
|---|---|
| `exercise` | 动作库（预置 + 自定义，`is_custom` 区分；只归档不删除） |
| `session` | 一次训练；`finished_at IS NULL` = 进行中；`template_id` = 这场按哪套计划练的 |
| `session_exercise` | 训练里的动作及顺序，`position` 决定界面先后 |
| `set_entry` | 每一组：重量、次数、完成状态、`rest_seconds`、`rest_started_at`、`completed_at` |
| `split_template` / `template_exercise` | 分化计划与它的动作清单（**只存清单与顺序**） |
| `app_meta` / `app_setting` | 库结构元信息（版本号）/ 用户偏好键值 |

三点全局约定：三个外键都写 `ON DELETE CASCADE`，但**级联要生效必须先开 `PRAGMA foreign_keys = ON`**（连接级，建库后立刻打开，测试适配器同样打开）；时间一律存**毫秒时间戳**（INTEGER）；布尔一律存 0/1。

### 5.4 核心流程

**记录一组**

```
用户点「✓ 完成这组」
   ↓ store/activeSession 更新内存状态
   ↓ repositories/setRepo.completeSet()   ← 立刻写 SQLite（不等训练结束）
   ├─ 记录 completed_at
   └─ 记录 rest_started_at，启动正计时
   ↓ UI 切到休息界面
```

**按计划开始一场训练**

```
用户点「开始训练」
   ↓ resume 探一次 → 有 current 就返回 'conflict'，不新建（不变量 1）
   ↓ 读 listTemplates + findLatestTemplateId
   ↓ domain/rotation.nextTemplateId  ← 纯函数决定今天练哪套
   ↓ createSession(name, templateId)   ← 定完计划再一次建，顺序不可反
   ↓ 按计划里的动作建 session_exercise 与第一组
```

> **调用顺序必须是「先探冲突 → 再定计划 → 才建 session」。** 轮转的输入是「最近一场已结束训练用的模板」，如果先把这一场建出来，虽它 `finished_at` 还是 NULL、不会污染那个查询，但顺序写成「先建后定」后很容易在后续改动里误用 `listSessions` 之类的接口把这一场算进去。**定完计划再一次建，是唯一不需要推理的顺序。**

**导入记录**

```
CSV（Strong / Hevy / 训记）        手动补记录表单
        ↓ parseWorkoutCsv              ↓
        └──────→ ImportedWorkout ←──────┘   ← 与来源无关的中间结构
                       ↓ domain/importRecords（写库前的检查：时间合法、非空）
                       ↓ importRepo.importWorkouts（整批一个事务）
                  session + session_exercise + set_entry
```

> **导入只有一条落库路径。** CSV 与手动补记产出同一种中间结构、共用 `importRepo`；两条路各写一份插入逻辑，差别一旦出现（比如一边写了 `completed_at`、另一边忘了），进步曲线会莫名其妙地点少，而这种 bug 极难定位。

### 5.5 界面信息结构

| 屏 | 它要回答的问题 |
|---|---|
| 训练首页 | 今天该练哪套（计划卡片 + 「第 2 / 3 套」）/ 有没有没练完的（「继续 今天 15:20 的训练 · 深蹲 等 3 个动作 · 已记 12 组」） |
| 记录页 | 当前这一组填多少 —— 屏幕上只有它，拇指不用移动 |
| 休息界面 | 歇了多久（正计时，不催）+ 「开始第 4 组」 |
| 训练总结 | 三个数字（时长 / 总组数 / 总容量）+ **次数数组原样**+ 粗略提示 |
| 历史列表 / 详情 | 哪天练了什么；详情与总结**共用同一套视觉与 `SessionSummaryView`** |
| 进步列表 | 练过的动作，按最近练过倒序，行上「最近一次日期 · 最重的一组」+ 迷你走势 |
| 动作详情 | 横向分页三张卡（最大重量 / 估算 1RM / 总容量），各带最好值、日期与折线 |
| 设置 | 训练计划 / 外观（主题三态）/ 备份 / 记录管理 |
| 计划列表 / 编辑 | 分化循环的顺序（上移下移）+ 动作清单 |
| 导入页 | 预览（场数 / 时间范围 / 涉及动作 / 单位换算 / 读不懂的行）→ 确认 |

**进步页三张卡的措辞刻意不同**：

| 卡片 | 头上的字 | 图上的一个点 |
|---|---|---|
| 最大重量 | `最好 · 日期` | 那一次训练里最重的一组（不论次数，并列取次数多的） |
| 估算 1RM | `最好 · 日期` + **`估算 · 仅供参考`** + 来自哪一组 | 那一次里所有可换算组中最好的一个 |
| 总容量 | **`最高 · 日期`** | 那一次所有已完成组的 `Σ(重量 × 次数)` |

**总容量不写「个人最好」** —— 容量是训练量，不是力量成绩，一个练得少但更重的日子容量反而更低。这正是不把三个口径说成同一件事的直接要求。

**「一次训练 = 一个点」**：真实数据里每一组的次数都不一样（`55×10 / 60×10 / 65×5 / 70×3`），所以同一次训练里**每组各算各的，然后取最好的那个**当作这一场的点。**不按组画点** —— 那样一天之内会来回锯齿，看不出「进步」。

> **两条容易搞错的语义，都用真实数字锁住了**：
> 1. **高亮点是"最大值"，不是"最新值"。** 容量在掉的时候，绿点会落在更早的那一次 —— 这正是它该做的。
> 2. **「最佳 e1RM」不一定来自"最重的那一组"**：`60×10` 的 e1RM 高于 `70×3`。测试里专门用这两个数字锁住这条语义。

**次数 > 10 时会缺点，这是必须承受的**：某次训练里所有组的次数都 > 10，那一次在 e1RM 曲线上**没有点**。处理方式是三选一里的刻意选择 —— **不补 0**（0 是「练得很差」，而事实是「这一场不适合换算」）、**不补估算**（正是被禁止的外推）、**线直接连过去**并在图下写一句「有 N 次训练没有可用于换算的组（次数 > 10）」。

### 5.6 视觉规范：力量感 · 暗色仪表盘

**概念**：把界面当成一台测量仪器来设计 —— 这个 App 的核心信息全是数字，**数字就是界面，其余都是标尺**。

**配色：铸铁 + 信号橙**。刻意避开 `#2b7fff` 蓝 / 紫蓝渐变（AI 生成界面的最典型特征）与荧光绿（与健身房「安全色」语义冲突）。信号橙同时是杠铃片、警示带、力量器械的颜色。

```ts
背景 #0B0C0E（近黑，不用纯黑——纯黑在 OLED 上和边框糊在一起）
表面 #141619 / #1C1F24（二级 / 按压态）
强调 #FF6A1A   成功 #32D74B   危险 #FF453A
文字 #F2F4F7 / #9BA1AC / #656B76   描边 #2A2E35
```

浅色主题是**同色相映射**，不是简单反色（暖白底 `#FAFAF8` + 略深一档的橙 `#E4580A`）。

**字体：系统优先 + `tabular-nums`，不引第三方字体文件。** 中文字体动辄 5–10MB 会拖慢启动；引拉丁数字字体则会制造中西混排差异。改用 `fontVariant: ['tabular-nums']` —— 数字宽度恒定，拖动那个 84px 的大数字时 `9 → 10` 不会让整块抖一下。**品牌感靠排版、间距、颜色做，不靠字体文件。**

字号尺度（**下面是 `src/ui/tokens.ts` 里的实际值**）：

```
display 84  记录页那个超大数字     clock 76  休息计时的钟面
stat 30     统计块里的主数字       h1 30     页面大标题
h2 22       区块标题              title 17  列表行主文本、按钮
body 15     正文                  caption 13 次要说明、元信息
label 11    分组小标题、单位标注（通常配 letterSpacing）
```

> 设计阶段写的是 `display 88`，落地时收敛到 **84**，并**多出了一档 `clock 76`** —— 休息计时的钟面与记录页的大数字是两个不同的尺寸，共用一个 `display` 会让其中一处偏大或偏小。**tokens 是唯一来源，界面不写裸数值。**

**动效只做两处，不做入场动画**（健身房场景要的是「立刻可用」，不是「好看地出现」）：数字变档的微反馈（补足已有触觉反馈的视觉确认）、休息计时的呼吸点（告诉用户「它真的在走」，而不是一个静止的 `00:00`）。两者都尊重系统「减弱动态效果」。实现用 RN 内置 `Animated`，不引 `react-native-reanimated` 的动画 API。

**主题必须是三态**，不是布尔：

```
system | light | dark
```

布尔（深/浅）表达不了「跟随系统」，而它才是默认值、也是大多数人想要的；做成布尔就得额外加一个「是否自动」的开关，两个控件互相耦合，比一个三选一更难用。其余四条实现约定：偏好存 `app_setting`；非法值退回 `system`（**主题读不出来不该让 App 起不来**）；**先改内存再写库**，写库失败不回滚（用户在设置页点一下必须立刻变色）；偏好读出来之前**不放行子树**（否则每次启动都会闪一帧）。

### 5.7 删除与计划的数据规则

**级联删除已经就绪**（两个外键都写了 `ON DELETE CASCADE` + 连接打开时 `PRAGMA foreign_keys = ON`），所以删一场训练只需要删 `session` 一行。

> ⚠️ **绝不要写 `DELETE FROM session WHERE id <> ?` 这类否定式 `NOT IN` 子查询。** `PRAGMA foreign_keys = ON` 下，SQLite 对 `session` 的删除会级联扫 `session_exercise`，而这条 DELETE 正在读 `session_exercise` → 报 `database table is locked`。单个 id 的删除不经过子查询，是安全的。

`deleteSessionExercise` 三句**必须按这个顺序**：

```sql
DELETE FROM set_entry        WHERE session_exercise_id = ?;
DELETE FROM session_exercise WHERE id = ?;
UPDATE session_exercise SET position = position - 1 WHERE session_id = ? AND position > ?;
```

重排是为了不留空洞 —— 留着空洞 `ORDER BY position` 也还能用，但以后要把动作插到中间（拖拽排序）就会错位，是个埋着的坑。

**删动作的两条分支**（判据与后果都必须说清）：

| 条件 | 行为 |
|---|---|
| 该动作**没有任何已完成组** | 直接删，不弹窗 |
| 已经记过组 | 弹窗：「『深蹲』已经记了 3 组」/〔删掉这 3 组〕〔先留着〕〔取消〕 |

- 「删掉这 3 组」→ `deleteSessionExercise`（组与动作一起消失，`position` 重排）
- 「先留着」→ `deleteIncompleteSetsOf`（删占位组、**留已完成的组**），界面按「**还有没有未完成的组**」把动作摘掉；而进步曲线只认「已完成且属于某场训练」的组，那 3 个点**仍在曲线上** —— 这是刻意的：用户选的是「别删我的记录」。
- **未完成的占位组必须一起删掉**：`completeCurrentSet` 每完成一组都会预建下一组，留着占位组，用户下次 `resume` 回来点「完成这组」会**毫无反应** —— 一个静默的假死按钮。
- `exercises.length === 1` 时**不显示删除按钮**，避免把最后一项删成空屏。

**`removeExercise` 必须把 `currentIndex` 夹回合法范围**（`Math.min(currentIndex, exercises.length - 1)`，列表为空时归 0）。不做就是一个崩溃点：删掉的正好是当前聚焦的动作时，`exercises[currentIndex]` 变成 `undefined`，记录页会掉进「这次训练还没有动作」的分支，而 store 里其实还有别的动作 —— **这个动作条与屏幕内容对不上的状态，比崩溃更难排查**。

**删除的文案必须写明后果**，不能只说「确认删除？」：

> **删除 9月16日 19:30 的训练？**
> 这条记录和它的 12 组会一起消失，进步曲线上也会少掉这一个点。删了不能恢复。

**删的正好是进行中的那一场时**：删完立刻 `reset()`。不清的话，首页「继续训练」会指向一条已经不存在的记录，点进去是一屏空白。

### 5.8 导入的规则

**预览页是导入的必经之路**，它必须写出：场数、时间范围、涉及动作（其中几个本机没有、将新建为自定义动作）、**单位换算（「12 行的磅已换算成公斤」）**、以及**读不懂的行数与原因**（可展开，带**文件里的真实行号**，用户能直接对着表格找）。

> `poundsConverted` 是设计时漏掉的字段 —— 换算之后公斤与磅在数据里完全相同，**事后从 weight 反推是不可能的**，所以这个计数必须由**解析器**算出来。这条是实施后补进接口的。

**解析层绝不猜**，必须处理的脏数据每一条一个测试：UTF-8 BOM、`\r\n`、字段内的逗号与引号、`60kg`、`135 lb`、`BW`/空（记 0 kg 且**不算读不懂**）、三种日期格式、只有日期没有时间（取当天 **12:00 本地时间** —— 零点最容易被时区处理推到前一天）、空行与重复表头（跳过但**不计入 skipped**，它们不是「读不懂」）。

**列名映射表**（表头先按规范化后的名字匹配 —— `trim`、全角转半角、连续空白折叠、大小写折叠 —— 三种来源各一张）：

| 来源 | 日期 | 训练名 | 动作 | 重量 | 次数 |
|---|---|---|---|---|---|
| Strong | `Date` | `Workout Name` | `Exercise Name` | `Weight` | `Reps` |
| Hevy | `start_time` | `title` | `exercise_title` | `weight_kg` | `reps` |
| 训记 | `日期` | `训练名称` | `动作名称` | `重量(kg)` | `次数` |

**四列必需**（日期 / 动作 / 重量 / 次数）；训练名缺失时退化成 `null`。

> **一处与设计阶段的偏离（落地时改的）**：设计里「组序」（`Set Order` / `set_index` / `组序号`）也算一列，实现**不读它** —— 组的先后已经在文件行序里了，多读一列只会多一个坏数据的入口。

**日期解释按「月在前」是刻意的**：Strong 与 Hevy 都是美国 App，导出的就是月/日/年。`1/2/2024` 这类写法两种解释相反，猜错会让整月的训练日期全部错位 —— **宁可让用户看到「第 N 行认不出来」，也不猜。** 同理，时间戳显式按**本地时区**构造（不走 `Date.parse` —— 它对无时区字符串的行为在不同环境不一致），并校验字段是否越界（`2 月 31 日` 会被 `Date` 悄悄滚到 3 月，那就是一条日期完全错误的记录）。

**每一行都读不懂时**：`workouts` 为空 → 预览页直接显示「这个文件里没有能识别的训练记录」并**只给「取消」，不给「确认导入」**。

**动作名匹配是唯一入口**，且有一份**必需**的缓存：42 场训练里「卧推」可能出现 300 次，每次都查一遍库是 300 次查询；而**每次各建一个新动作则会让进步曲线被切成三百段** —— 这是导入功能最容易踩、事后最难修的坑。

**写进去的每一组**：`is_completed = 1`、`completed_at = finishedAt`、`rest_seconds = NULL`、`rest_started_at = NULL`。**没有真实的组间休息数据，编一个平均值比留空更糟** —— `restAdvice` 要算平均休息时长，假数据会把它带偏。

**整批一个事务**：几百场训练逐条 INSERT 在手机上会读秒，事务是唯一能让它可接受的做法，顺带买到「要么全成、要么全不动」。失败时抛**原始异常**（事务已回滚，库里没变）。

**没有动作、或所有动作一组都没有的「训练」一律拒绝**：空训练进了库就是一条点开什么都没有的历史记录，用户既看不懂也删不掉。CSV 里这种行是解析不出组的坏数据，手填时是用户还没填完就点了保存 —— 两种都该拦在**写库之前**。

### 5.9 备份：格式 v2，且 v1 必须仍能导入

- `BACKUP_VERSION` 1 → 2；`BackupData` 加 `templates` / `templateExercises`。
- **`version 1` 的老备份必须仍能导入**：缺失字段按空数组 / `null` 处理。不做这条兼容，**用户手上已经导出的备份文件就当场作废** —— 那是比新功能没做更严重的问题。
- `version > 2` 仍然拒绝。
- `validateBackup` 增加引用完整性检查（`templateExercise.templateId` 必须在 `templates` 里、`exerciseId` 必须在 `exercises` 里）。
- `exportAll` 按 `rowid ASC` 多导两张表；`importAll` 的删除顺序在前面插入 `template_exercise → split_template`（**必须在 `exercise` 之前**，因为 `template_exercise.exercise_id` 引用 `exercise(id)`），插入顺序在 `exercises` 之后。

**它的验收方式值得记下来**（09-21 真机 6 项）：导出后 `pm clear` 清空数据 → 导入 → **逐字段比对导入前后的训练详情**（时长 216 分钟 / 5 组 / 320+1260=1580 kg / 次数数组 `[8 / 8]`、`[8 / 8 / 8]` 全部一致）；再拿两个坏文件（`this is definitely not json`、`{"hello":1}`）各验一次，都被 `validateBackup` 拦下、**一个字节都没写库**。

> **备份是这个 App 里唯一会"永久损失用户资产"的缺口** —— 所以验收方式也必须是对抗性的（清空 + 坏文件），而不是"导出成功"就算过。

## 6. 质量保证

### 6.1 三层验证，各自能抓什么、抓不到什么

| 层 | 规模 | 跑法 | 能抓 | 抓不到 |
|---|---|---|---|---|
| **单元测试**（分层） | **25 套件 / 304 条断言**，约 18 秒 | `npm test` | 纯逻辑、仓储、store 各自的正确性 | **层与层之间假设不一致** |
| **端到端回归** | `verify/e2e.test.ts`，1 个用例串起 **5 条主旅程** | `npm run verify:e2e` | 用户实际走的那条链 | 渲染、手势、原生模块 |
| **真机验收** | 每轮一份验收表 | adb 驱动 + 截图取证 | 手感、原生差异、真实数据 | 费时且不可自动化 |

**为什么必须有第二层**：「按计划开训练 → 练完 → 结束 → 再看轮转」这一条链跨了 `domain/rotation` / `templateRepo` / `sessionRepo` / `setRepo` / `store/activeSession` **五处**，而没有任何一个分层测试覆盖它。分层全绿仍然可能因为层与层之间的假设不一致而在真机上坏掉。

**它已经证明了自己的价值**：这条链**第一次跑就抓出一个分层测试没抓到的问题**（§4.2 那个判据错误）—— 根因是界面判「一行 set 都没有」，而 `keep` 会保留已完成的组，条件恒不成立；当时分层测试里那条用例**也写错了同一个判据**，两边同时错的时候只有端到端能发现。这就是它值得留在仓库里的理由。

**它不覆盖什么必须写清**：渲染、手势、原生模块，以及真机上 `expo-sqlite` 与 `node:sqlite` 的实现差异 —— **不能替代真机验收**。

### 6.2 测试策略里有意的取舍

- **jest 的 `testMatch` 只收 `src/**/*.test.ts`**，所以 `app/` 下的页面没有单元测试，靠 `tsc` + 真机验收。
- **Babel 只配了 `@babel/preset-typescript`，没有 JSX 预设。** 这带来一条纪律：**纯逻辑留在带 JSX 的文件里等于永远测不到** —— 遇到这种情况是把函数移进 `.ts`，不是去改测试基础设施。
- **`--runInBand`（`maxWorkers: 1`）不是性能选择，是环境要求**：沙箱禁止子进程管道 stdio，worker 池会 `spawn EPERM`。
- **不要写会随机变红的测试** —— 时间相关断言必须显式固定时间戳，不要依赖「两次调用恰好落在同一毫秒」。曾有一条 `expect(second.startedAt).toBe(first.startedAt)` 的测试，实测 **20 次全量闪 2 次**（差 1 毫秒）；改成显式把两行时间戳设成同一个值、让并列成为**确定事件**后，25 次 0 失败 —— 测的是 SQL 排序语义本身，而不是运气。
  > **一条会随机变红的测试，比没有测试更危险 —— 它会训练所有人忽略红色。**
- `verify/` 放在 `src/` 之外，所以 `npm test` 不会带上它（不拖慢日常反馈），需要时单独跑。

### 6.3 验收的纪律（三条都是踩出来的）

1. **静态自查不等于验收。** `tsc` 与 `jest` 全绿**不代表任何一项已在真机上通过**。10-07 那一轮的 12 项真机验收**全部未做**（收尾机器 `adb devices` 是空的），文档里如实写成「未做」，不写成「通过」。
2. **真机自动化截图会被息屏骗到。** 手机自动锁屏后 `adb shell screencap` 会返回**上一帧而不是报错**，曾因此拿到一张和半小时前**哈希完全相同**的「新」截图，并据此得出错误结论。应对：`adb shell svc power stayon usb` + 用 `uiautomator dump` 核对前台窗口。
3. **验收前先查构建记录。** 判断手机上是什么版本，查 EAS 构建记录（`eas-status.cjs` 直接打 GraphQL API，不需要 spawn 子进程），**不要信文档里的时间戳推断**。

## 7. 实施历程留下的教训

### 7.1 真机反馈是设计的一部分

Task 8 完成后用户带去健身房用了一次，提的三条意见**全部属实**，其中一条是**功能性缺口**（换不了动作 —— App 无法完成任何一次真实训练）。这正是「M2 之后就能拿去用」这个里程碑设计的意义：**早一步拿到真实反馈，胜过晚一步做完美。**

**但这个优点的背面是一条硬约束**：因为 `app/` 与组件按策略不写单测（§6.2），**界面缺陷只有真机用一次才会暴露** —— 「换不了动作」这处缺口，在当时的 **79 条断言**里一条都照不到（那 79 条全在 `domain/` 与 `repositories/`，连 store 层都还没有测试）。真机验收因此不是可选项，而是**唯一能照到界面与手感的层**。

**一项不需要真机的补强**：`tsc` 与 `jest` 都覆盖不到「整个 App 到底打不打得成包」。所以可以在真机之前用 Metro 打一次完整 Android dev bundle 并按字节确认新代码进包（实测 `HTTP 200，7,038,298 字节`）。两个陷阱：**Metro 把中文转成 `\uXXXX` 大写十六进制转义**，必须用转义形式搜；bundle 里出现的 `Unable to resolve module` / `TransformError` 字样**是 RN 自己的错误模板源码**，不是真错误。

### 7.2 环境限制会伪装成代码错误

| 现象 | 真相 |
|---|---|
| jest `spawn EPERM`、Hermes 编译失败、ngrok 失败 | 沙箱禁止子进程管道 stdio |
| `IO exception while downloading manifest` | 沙箱不让写 `~/.android` |
| `Failed to download any source lists` | 本地权限问题 |
| `EPERM: mkdir 'C:\Users\mobis\.expo'` | 沙箱外的家目录不可写 |
| `git --help exited with status undefined` | 又是 spawn 读输出被拦 → 用 `EAS_NO_VCS=1` |
| 本地 Gradle 构建失败 | **不是权限，是网络下载量上限** —— 能下 1MB，下不动 2GB。云构建把它消掉：只上传 3.1MB 源码 |

三条通用规律：

1. **报错信息几乎总是指向错误的方向。**
2. **凡是「工具想把东西写到用户目录」的地方，都要预先重定向。** 已踩到五个：`.expo`、`.android`、`.gradle`、`AppData\Roaming\eas-cli-nodejs`、`_npx` 缓存；而且 **`USERPROFILE` 不够，`APPDATA` / `LOCALAPPDATA` 要单独设**。
3. **超时类失败先把超时和重试调大再下结论** —— npm 那次差点被误判成「网络挂了」，实际 30 秒就装完了。

**另外两条具体教训**：

- **在依赖不可达的环境里，不要用包管理器去试装依赖。** 一次失败的 `pnpm add -D sql.js` 把 **40 个包**（含 `expo`、`react-native`、`expo-sqlite`）重命名进了 `node_modules/.ignored`，项目当场编译不了。**这不是删除，是移动，所以逐一移回即可完全复原。**
- **先看看 `.superpowers` 下有没有现成的** —— 沙箱不但拒绝在工作区外写，也拒绝在 `node_modules` 里新建目录。

### 7.3 协作与流程教训

- **并发提交事故**：两个 subagent 并行时撞了共享 git index，两条改动挤进同一个提交。**之后的规则：subagent 一律不碰 git** —— 只写文件、跑测试，提交全部由主 agent 在每个 Task 之间完成。
- **红灯交回来是对的**：M4 的 Task 4 出现「测试与实现自相矛盾」（实现取「同重量时次数多的那组」，测试却断言取先出现的那个）。subagent 没有自行改断言、也没有为了变绿去改实现，而是把红灯交回来 —— **处置正确**。同样重量多举 3 次显然是更好的一组，于是改的是测试那一行。
- **计划里的顺序也可能错**：M4 的 Task 6/7 必须互换 —— Task 6 要 `router.push({ pathname: '/exercise/[id]' })`，而 expo-router 的 typedRoutes 类型是预生成在 `.expo/types/router.d.ts` 里的，那条字面量要等路由文件建出来才会有；且该文件在 `CI=1` 下**不会**重新生成。**实际顺序：Task 7 → 重新生成路由类型 → Task 6。**
- **一行注释能防一类 bug**：`sessionRepo.listSessionSummaries` 的注释里写明「N+1 查询在手机上会肉眼可见地卡」，后来 `progressRepo` 就照它做成了**一次全取、在 JS 里分组**（一份 SQL、两个调用方，不复制）。
- **重复的坑要写进注释**：`rowid` 兜底这个坑在代码注释里写了两次，第三次就不必再踩。
- **计划的复选框是文档的一部分，不回填就等于没做。** 这一条是 M5 那轮自己写下的，而它同时也是**这套文档体系目前最大的欠账**：

  | 计划文档 | 复选框回填 |
  |---|---|
  | M1+M2 | **0 / 88** |
  | M3 | **0 / 24** |
  | 训练生命周期 | **0 / 50** |
  | M6–M8 | **0 / 100** |
  | M4 | 13 / 42（部分） |
  | M5 | 8 / 26（09-21 用「实施与验收状态（补记）」追认） |
  | `m2-acceptance-checklist.md` | **20 / 20**（唯一全勾的） |

  也就是说，**除了验收清单，所有「做了什么」的证据都不在计划文档里，而在 spec 的实施记录、提交历史与验收清单里** —— 这正是本文存在的原因之一。另有一个具体缺口：M5 的「变异测试」步骤**无法从仓库状态反推是否真做过**。
  > 教训：**这类步骤应当把结论写进提交信息。**

## 8. 决策台账（含被否决的选项）

| 决策点 | 选择 | 被否决项与原因 |
|---|---|---|
| 技术栈 | Expo / React Native | PWA 计时不可靠且迁移会丢数据；原生 Android 环境成本过高 |
| 数据存储 | 纯本地 + 留同步接缝 | 直接上云同步会让工作量翻倍，且尚未验证产品价值 |
| 记录界面 | **聚焦当前组（B）** | 全览列表点击目标小；列表 + 操作条空间紧张 |
| 休息计时 | **正计时** | 倒计时会催促用户，且数据是「规定」出来的而非「观察」出来的 |
| 训练后反馈 | **本次训练内简单对比次数数组** | 跨训练统计推断已被否决：文献本身对最优休息时长无共识，且同一个人不同训练日反应差异明显；RPE 手动评分与「越快越好」冲突，实际会被荒废 |
| 反馈的语气 | **必须包含正反馈分支** | 只挑毛病、从不肯定，用两周就会被无视 |
| 指标呈现 | **区分「口径」与「估算」，都标注适用范围** | 把估算值当实测值展示；把某一种 volume 口径当成唯一定义；1RM 用单一公式却不说它只是几个公式之一 |
| 饮食热量 | **不做** | 需要食物数据库与宏量营养计算，工作量可能超过核心记录功能本身 —— 最容易吞掉整个项目的坑 |
| 训练模板 | 原定推迟到 v1.5，**10-07 提前做了** | v1 的「沿用上次组数 + 预填上次重量」当初被认为已覆盖大部分便利性，**但真机使用证明它不成立**（§2.2） |
| 云同步 / 账号 / 社交 / 排行榜 | 不做 | 本 App 的定位是单机；社交与排行榜明确划到 v2 之外 |
| 视觉气质 | **力量感 · 暗色仪表盘** | Clean 精炼白底（白天好看，健身房灯光下刺眼）；硬核工业粗野排版（个性最强但可读性风险高） |
| 强调色 | **信号橙** | `#2b7fff` 蓝（AI 味最重）；荧光绿（与「安全色」语义冲突） |
| 字体 | **系统字体 + `tabular-nums`** | 引中文字体文件（5–10MB，拖慢启动）；引拉丁数字字体（中西混排不一致） |
| 动效 | **只做两处，不做入场动画** | 编排式入场动画（健身房要立刻可用，不要「好看地出现」） |
| 主题 | **三态 + 两套都做** | 只做一套（`app.json` 已声明 automatic，不做等于留一个半坏状态）；布尔两态（表达不了「跟随系统」） |
| 预览数据库 | **内存演示执行器** | 装 `sql.js`（npm registry 本机不可达）；直接用 `expo-sqlite` 的 wa-sqlite（靠 Web Worker，Metro 静态 web 打包器不支持 worker 分块，源码里是断言，无开关） |
| 进步页图表 | **手绘 `Polyline` + `Circle`** | 引图表库（这里只有折线和圆点，引库反而要跟它的样式打架） |
| 进步页时间窗 | **不设**（「最好」= 历史最好） | 「最近 90 天」（用户数据量还小，加窗口只会让他以为自己退步了） |
| 计划里存什么 | **只存动作清单与顺序** | 存目标组数/重量/次数（每改一次计划都要维护几十个数字，且与「上次练了多少」形成第二真相） |
| 轮转状态 | **从 `session.template_id` 推导，不单独存指针** | 存「下一个该练第几套」（要在四条路径上同步维护，一旦不符就是「莫名跳了一套」） |
| 计划排序 | 上移 / 下移按钮 | 拖拽排序（要引手势与动画复杂度，只换来「少点几下」，且两个界面都要做一遍） |
| 相邻 position 互换的写法 | **三步：挪到临时位置 −1 → 目标行补位 → 被移动行落位** | 「两句 `UPDATE ... WHERE position = ?` 对调」与「先 SELECT 出 id 再按 id 定位」（在无唯一约束的列上都会**静默失效**，见 §2.2 末行 —— **这类 SQL 不要靠推理，在真实引擎上跑一遍**） |
| 训练中改动作顺序 | **不做**（只加、只删） | 临时调顺序的价值小于它带来的手势复杂度 |
| 跳过某一套 | 不加独立按钮 | 「换一个计划」就是它 |
| 导入落库路径 | **只有一条**（共用 `importRepo`） | CSV 与手填各写一份插入逻辑（差别一旦出现，进步曲线会莫名缺点，极难定位） |
| 备份兼容 | **v1 老备份必须仍能导入** | 只认新格式（用户手上已导出的备份文件就当场作废） |
| web 预览缺功能 | **隐藏入口** | 给 `demoExecutor` 补 SQL 分支（按形态匹配，成本随功能增长） |

## 9. 环境的现实约束

这台开发机器不是一台普通开发机，设计里凡涉及「能不能跑起来」的判断，都以这一节为准。

| 限制 | 表现 | 解法 |
|---|---|---|
| 子进程管道 stdio 被禁 | jest `spawn EPERM`、Hermes 编译、ngrok、eas-cli spawn 全部失败 | jest 固定 `maxWorkers: 1` / `--runInBand`；不用 `expo export` 和 `--tunnel`；用 `EAS_NO_VCS=1` |
| 沙箱外的家目录不可写 | `.expo` / `.android` / `.gradle` / `AppData\Roaming\eas-cli-nodejs` 全部 EPERM | 启动前把 `USERPROFILE` **和 `HOME`、`APPDATA`、`LOCALAPPDATA`** 指向工作区内目录 |
| 遥测写入沙箱外 | Expo 命令直接崩 | `EXPO_NO_TELEMETRY=1` |
| TLS 中间人代理 | Node `unable to verify the first certificate` | Node 下载加 `--use-system-ca` |
| 后台进程被回收 | adb 守护随命令结束而死，隧道断 | adb 服务必须作为**常驻后台任务**运行 |
| 局域网 / 隧道不可用 | 防火墙三 profile 全开且无入站放行 | **USB + `adb reverse`** —— 数据走数据线，不经过网络，防火墙管不着 |
| WMI / CIM 查询被拒 | `Get-NetIPAddress` 等全部「拒绝访问」 | 用 `ipconfig` / `netstat` / `netsh` 替代 |
| 网络下载量上限 | 本地 Gradle 构建下不动依赖 | **EAS 云构建**（只上传 3.1MB 源码；实测上传 25 秒、构建约 20 分钟） |

**真机调试的标准流程**（完整版见 [`dev-environment-notes.md`](../plans/dev-environment-notes.md)）：常驻 adb → `adb reverse tcp:8081 tcp:8081` → `USERPROFILE` 重定向后 `npx expo start --localhost` → `adb shell am start` 拉起 → **`adb shell screencap` 拉回本地看图**（不要用 `exec-out ... > file.png`，PowerShell 会破坏二进制流）。

**Expo Go 版本必须匹配 SDK**：商店版永远是最新版（当时是 SDK 58，本项目是 SDK 57），必须装匹配的 APK，且**先卸再装**（直接装会因版本降级失败）。

## 10. 已知限制与待办

### 10.1 未解决的设计问题

**「进行中的训练」不加时间上限，对存量异常数据不成立。** 当时的理由是「正常流程下根本不会留下未结束的训练，会留下的只有误杀」，但**旧包持续产生的未结束训练会一直留在库里** —— 用户库里实测有 2 场 9/16 的残留，清理它们的代价是历史里多几条像「1686 分钟、0 组」那样的记录。

**这是「不加兜底」这个决定需要重新考虑的现实证据，目前只被记录、没有被解决。** 处置方式待定。

### 10.2 未做的验证

**10-07 那一轮的真机验收 12 项全部未做。** 收尾机器上 `adb devices` 是空的（没有连接任何设备），因此不只是「本来就要在手机上跑」的几项，而是**全部**。那批改动只经过 `tsc --noEmit`（退出码 0）与 `jest`（25 个测试文件 / 304 条断言全绿）的静态自查，以及端到端回归这一层补做验证。

同一次收尾里还有 **3 项与真机相关的检查未勾**：

1. 12 项验收逐条在真机上跑；
2. `npx expo run:android` 验证 **v3 迁移对老库的升级**（现在只有迁移单测与端到端覆盖，**没有在真机老库上跑过**）；
3. 用**旧版本导出的备份**在真机上导入一次（格式 1 兼容性只被单测覆盖）。

**静态自查不等于验收。** 上面这些改动**不代表任何一项已经在真机上通过**。

### 10.3 已知限制（明确接受）

- **网页预览看不到新功能的效果**：计划管理、删记录、导入在预览里不可用（入口已隐藏，§4.5）。
- **`node:sqlite` 与 `expo-sqlite` 的实现差异**覆盖不到。
- **`resume` 的不精确场景**：切到第 4 个动作但一组都没做就被杀 → 会回到第 3 个动作。
- **e1RM 曲线会缺点**：整场次数都 > 10 的训练没有点（不补 0、不补估算，只加一句说明）。
- **数据少时曲线只有两三个点**，看起来不像「曲线」—— **真话比好看的图重要**，空态与稀疏态都有专门文案。
- **文档里的版本推断会过期**：判断手机上装的是什么版本，查 EAS 构建记录。

## 12. 附：口径速查

写代码、改文案、审设计时，这一节是查证口径的唯一去处。

| 说法 | 精确定义 | 界面必须带的话 |
|---|---|---|
| **容量负荷 / volume load** | `Σ(weight × reps)`，只累加 `is_completed = 1` 的组 | 「总容量（重量 × 次数）」 |
| **估算 1RM（e1RM）** | `(Epley + Brzycki + Lombardi) ÷ 3`，只在 `2 ≤ r ≤ 10` 计算 | 「估算 · 仅供参考」+ 来自哪一组 |
| **个人最好** | 只用于最大重量与 e1RM | 容量那张卡写「最高」，**不写「个人最好」** |
| **组间休息** | 本组做完到下一组开始之间的时长，存在**本组**上；用时间戳算 | 「粗略参考」；建议增量固定 15 / 30 秒 |
| **进行中的训练** | `session.finished_at IS NULL` 且 store 里 `finishedAt === null` 的那场 | 「继续 <日期时间> 的训练」 |
| **当前计划** | 按轮转规则算出来的、这一场该练的那一套 | 「第 N / M 套」 |
